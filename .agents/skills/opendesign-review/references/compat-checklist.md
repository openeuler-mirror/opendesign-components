# 兼容 Checklist（向后 + 向前）

> **何时读本文：** 工作流第 2 步 Standards 轴，变更触及公开面（props、导出、CSS 变量、DOM 结构、class 名）时逐项过。每条配机械可查的命令，结论记「已查 / 不适用」。兼容检视的目标是**使用者视角**：变量还在 ≠ 行为没变。条目 1–8 检**向后兼容**（新库消费旧用法），第 9 条检**向前兼容**（旧库消费新用法）。

| #   | 条目                 | 查法                                                                                                                                             |
| --- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | 导出面               | `git diff <mb>...<head> -- packages/opendesign/src/index.ts` 及各组件 `index.ts`：删了 / 改了什么导出                                            |
| 2   | props 语义与默认值   | 对照 `types.ts` diff：删除是破坏，**语义 / 默认值变化同样是破坏**，不比删除轻                                                                    |
| 3   | 全库内部消费方       | `grep -rn "<组件名>" packages/ --include=*.vue --include=*.ts -l`：库内还有谁在用；回归是否落在「隔离墙」内（内部消费方可一并验证）              |
| 4   | 公开 CSS 变量        | 对照组件文档 CSS 变量表。**区分「变量消失」与「变量语义变了」**：变量还在、但 JS 侧布局效果退役，仍是使用者可见的语义变化，ReleaseNote 必须披露  |
| 5   | DOM 与 class 契约    | 根元素标签、class 名、层级变化——使用方的 CSS 选择器可能依赖；有破坏性变化须在 ReleaseNote 披露                                                   |
| 6   | SSR 与水合           | 渲染时序变化（编程滚动、挂载后测量）是否引入 `window` 依赖；对照该组件 `*.ssr.test.ts` 是否覆盖                                                  |
| 7   | 并行维护线           | 同一修复落 `release/1.2.x-spN` 双线时：`git diff <线A> <线B> -- <文件>` 核对「两线源码一致」声明；移植约定为**单向 cherry-pick**，不反向 merge   |
| 8   | 版本与披露           | ReleaseNote 条目与实际变更对照（使用者视角，判 release-note skill）；版本号惯例见 SKILL.md「环境事实」，`package.json` 落后 ReleaseNote 不算缺陷 |
| 9   | 向前兼容（跨线消费） | 新增枚举值 / 新增配置字段时，旧版本库收到是否安全降级：渲染分支有无 default 兜底、类型校验是否抛错（判定口径见下节）                             |

## 向前兼容判定（第 9 条展开）

方向区分：向后兼容 = 新库消费旧用法（条目 1–8）；向前兼容 = **旧库消费新用法**。

**触发场景（本仓特有）：** 双线并行——使用者业务代码同时服务 `release/1.2.5` 与 `release/1.2.7` 两线，代码里写了新枚举值 / 新配置字段，跑在旧线上；另含持久化配置（列配置等 JSON）新字段流进旧版本。

**会破的信号：** 新增 prop 枚举值但旧库渲染分支（switch / 映射表）无 default 兜底 → 空白或抛错；新增字段但旧库主动校验未知 key 并 throw。

**框架兜底不算缺陷：** Vue 对未声明 prop 静默忽略、多余 attrs 透传根元素——默认即向前兼容，不要把「未知 prop 被忽略」报成问题。

**裁决级别：** 健壮性加分项，通常以「降级建议」写入报告（补 default 兜底 / 忽略未知字段），不作合入阻塞——除非 spec 明确要求跨线共享，或旧线行为是抛错而非静默。

## 疑似 breaking 的判定与版本线裁决

上表 1 / 2 / 4 / 5 条命中任何一条信号，即进入 breaking 判定，产出三档结论之一：**无 / 疑似 / 确认**。

**信号清单**（触发即判，不限于这些）：props 删除、重命名、默认值或语义变化；导出删除或签名变化；CSS 变量删除或语义变化；根元素标签 / class 名 / DOM 层级变化；新增 `peerDependency`。

**裁决口径**（唯一标准）：**使用者是否可能已经依赖旧行为**。

- 「修 bug」不是豁免：修复 bug 行为本身通常不算 breaking（使用者不该依赖 bug 行为），但**顺带改了公开契约**（默认值、DOM 结构、CSS 变量语义）仍是 breaking——改的是契约，不是 bug。
- 「内部实现」不是豁免：变量还在但 JS 侧效果退役，是语义变化（上表第 4 条）。
- 灰色地带标「疑似」：列出信号 + 旧行为描述 + 谁可能依赖的证据，交作者 / 维护者裁决，**不得自行放行也不得自行阻塞**。

**版本线规则**（breaking 并非绝对禁止，但受 base 分支约束）：

| base 分支                      | 确认 breaking                                                                                                                                    | 疑似 breaking                  |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------ |
| `master`（主线，下一常规版本） | 允许合入，但必须同时满足：ReleaseNote 入 `### BREAKING CHANGES` 分区并写迁移方式；相关 commit 加 `!` 标记；compat-checklist 第 6 条 SSR 影响已查 | 报告列证据，请作者澄清后再归档 |
| `release/1.2.x-spN`（补丁线）  | **合入阻塞**：要求换 base 到 `master`，或把 breaking 部分从本 MR 拆出                                                                            | 合入前必须裁决，不得带疑合入   |

补丁线上的「修 bug」MR 尤其要过这重判定——溢出折叠、布局重构类修复最容易顺带改公开契约。

## SSR 判定信号（第 6 条展开）

- `setup()` / `render()` / 模块顶层访问 `window` / `document` / `navigator`（SSR 阶段不存在）——`git diff` 里新增的此类引用逐个看；
- 行为从「渲染期确定」移到「挂载后测量」（编程滚动、容器裁切、ResizeObserver）——用共享 helper `runWithoutGlobals`（见 component-testing skill）可验证真 Node 环境；
- 对照该组件 `*.ssr.test.ts` / `*.ssr-node-env.test.ts` 是否覆盖新路径，未覆盖列入测试缺口；
- 判定口径与 breaking 联动：SSR 渲染输出变化（结构 / 顺序 / 条件渲染）本身就是水合风险，疑似 breaking 按上节裁决。

## 检视口径

- 「正常」的判定要给证据：某条目查完没问题，报告写「已查 + 命令」，不写「应该没问题」。
- 兼容结论与 ReleaseNote 联动：第 4 / 5 条发现语义变化时，顺带核对 ReleaseNote 是否披露（缺披露按 Standards 轴缺陷报）。
- 内部消费方（第 3 条）落在改动影响内时，在报告里点名文件，供作者回归时按「单文件 → 组件目录」逐步扩大。
