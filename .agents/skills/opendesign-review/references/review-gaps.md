# 检视空白清单

> **何时读本文：** 工作流第 5 步聚合报告前——对照本清单声明「本次没覆盖什么」。这些维度在常规 diff 检视中天然漏掉（MR #931 从头到尾没覆盖），不声明就等于隐式声称已检视过。

| 维度         | 检查点                                                                                                         |
| ------------ | -------------------------------------------------------------------------------------------------------------- |
| 弹层交互     | 弹层定位与宿主元素 `transform` 钉边的相互作用；弹层内容列表的渲染时序                                          |
| 浏览器兼容   | `clip-path: inset()`、`overflow-x: hidden` + 编程 `scrollTo` 在 Safari / iOS 的行为差异                        |
| CI 稳定性    | 新增测试的固定等待（`wait(500)` 类）累计时长；单文件用例数 × 平均耗时是否推高 CI（如 30 例约 38s）             |
| 可访问性     | `visibility: hidden` 与键盘 Tab 序列的关系；focus 触发容器自动滚动的路径                                       |
| 多主题       | spec 要求「所有主题下正确」的效果（渐变遮盖类）是否在 light + dark 双主题都验证过                              |
| 提交可移植性 | spec 若要求可 cherry-pick 的逻辑单元提交，核对实际提交粒度是否混合（如要求 3 个可移植提交、实际 9 个混合提交） |

## 用法

- 逐项判断「本次是否覆盖」：覆盖了的写结论，没覆盖的**点名列入报告开头的「没验证什么」**。
- 本清单是声明工具，不是强制检查单——把每项都展开测会撑爆检视预算；价值在于让空白显式化，留给作者、后续检视或 CI 决定要不要补。
- 发现新的系统性空白维度（连续多个 MR 都漏的），加进本表。
