# 探针与实测方法

> **何时读本文：** 工作流第 3 步「探针实测可疑点」触发时——结论涉及几何 / 视觉 / 像素 / 滚动 / 布局，或需要评估测试是否真的拦住了缺陷。

## 探针写法

- 命名 `<name>.probe.test.ts`，置于临时路径或 worktree 内，**不落进** `src/<comp>/__tests__/`。
- 探针用例打印真实值：`getBoundingClientRect()`、`scrollLeft`、内联 style、`resolveTokenPx()`（见 [`component-testing`](../../component-testing/SKILL.md) 共享 helper）。断言可有可无，打印输出必须留下进报告。
- 探针是检视产物，不是测试资产：结束立即删，`git status` 核验（实测教训：临时探针曾两次忘记清理）。

## 实测裁决（为什么算术不够）

反例（MR #931，OTab 溢出折叠）：让位身位 `padding-right = navGapNumber + ellipsisWidth`，检视者用算术推出「末页签右缘距省略号左缘 = gap」，自我说服为「多留一个 gap，intended，略有富余」后放过。实测（600px 容器 / 10 页签 / medium）：`lastRight=518、shadowLeft=542、ellipsisLeft=550`——纯空白 24px，与三处自述全部矛盾（`navListStyle` 注释「末尾页签右缘止于省略号本体左缘」、ReleaseNote「尾部空白消失」、demo 文案「页签栏右端始终被内容填满」），而「尾部无空白」正是该 MR 的核心验收标准。

规则：

1. 算术结论 = 假设；实测数字 = 结论。
2. 数值与注释 / 文档 / 验收标准矛盾 → 默认其中一方有错，实测判定；「设计如此」不是解释，是消解矛盾的自我说服。
3. 报告里几何类结论的证据栏只接受实测数字。

## 红绿反证

判断新增测试是否空转：在 worktree 中把实现换回 base 版本，只跑新测试——

- **应当变红**：证明用例真的约束了新实现（MR #931 实测 17 红 / 13 绿，红的部分有效）。
- **仍绿的用例逐条检查**：是不是「特征化护栏」——只锁定现状、不约束目标行为的断言。这类用例要标注出来，不计入目标行为的覆盖。
- 反证跑完还原 worktree，主工作区不动。

## 覆盖状态清单

把测试当「已覆盖状态清单」读，主动列出**未被采样的状态**，逐条问「这条验收标准在哪个状态下被采样了」：

- **滚动类**：起点 / 中途 / 终点。MR #931 的缺口即在此——「尾部无空白」只在 `scrollLeft=0` 采样，滚动终点只断言上界，空白再大也全绿。
- **交互态**：运行时改 prop / class、断点往返、主题切换。
- **组合**：尺寸 × 溢出 × 数量（如 size 三档 × 溢出与否 × 页签数）。

每个确认缺陷回填一句「为什么测试没拦住」，定位到具体采样缺口——作者才知道该补哪条断言，而不是笼统地「补测试」。

## 对照实验规则

- **不原地改被测对象**：对元素 `style` 原地赋值再测，会污染被测状态得出无效对照（MR #931 实测踩坑）。正确做法：改输入 → 重新挂载 → 再测。
- **`scrollWidth` 可能虚高**：钉边元素的 `transform` 会把 `scrollWidth` 撑大（省略号钉边场景，正是被检视代码注释里写过的坑）。滚动最大值优先复用组件自身的 clamp 值，不信任元素 `scrollWidth` 后直接 `scrollTo`。
