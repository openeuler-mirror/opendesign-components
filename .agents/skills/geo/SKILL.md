# 组件库 GEO 分析与方案指南

> **这是什么:** 一套可移植的方法,指导你对**任意组件库**(Vue/React/Svelte 等)做 GEO(生成式引擎优化)分析——审计渲染产物的 AI 可读性、诊断差距、提出分阶段方案。本 skill 只教方法;某个具体库的结论,由该方法在该库上跑出来,落到**该库自己的**文档里(见工作流第 5–6 步)。skill 不携带任何具体库的决策或现状。

> **详细参考按话题分放在 references 目录下:**
>
> - **调研结论**(GEO 是什么、什么有效、代理图谱、ARIA、schema.org、诚实张力)→ [`references/findings.md`](references/findings.md)
> - **L1 杠杆清单**(渲染产物杠杆 / 不要做 / 向后兼容风险)→ [`references/levers.md`](references/levers.md)

## 核心原则(保持诚实,防止过度承诺)

1. **范围是选择项,先和用户定。** GEO 改造可作用于三层:**L1 库产物**(组件渲染的 HTML/ARIA)、**L2 文档站**(SSG / 站点结构化数据)、**L3 消费方应用**(站点基建 / 内容 / 可抓取性)。不要假定只做哪一层——先确认诉求落在哪。不同层的杠杆、成本、回报差很多:L1 是库本身职责,L2/L3 越界到应用侧,库使不上劲。

2. **目标也是选择项,默认 a主b辅。** 三个可能目标:(a) 内容引用(被生成式引擎在答案中引用/转述)、(b) 代理可操作(读无障碍树的 AI 代理能识别并操作组件)、(c) AI 编码工具认识组件。默认推荐 **a 为主、b 为辅**(库的 GEO 价值最终落在引用);(c) 通常不作北极星——它是"让 AI 用库开发",与 (a)/(b) 不同轴,本 skill 不把它当杠杆(见原则 4)。**但收敛到 L1 这一面,证据常把优先级翻转为 b主a辅**(见原则 3 与 `findings.md`「诚实张力」)——提方案时按所在面的真实证据排优先级,别让 L1 承诺它给不了的 (a)。

3. **证据为本,标注强度。** 区分:**已证**(GEO 论文:加引用/统计/引文 +~40% 可见度,但测的是**内容**非 HTML)、**推断**(语义 HTML → 更好抽取 → 引用,未证)、**薄**(ChatGPT/Perplexity 抽取方式未公开)。**不得宣称"语义 HTML/ARIA 能提升 AI 引用率"——这是推断不是事实。** 不得把 (b) 的 ARIA 说成对视觉代理(Anthropic computer-use、OpenAI Operator)有益——它们是像素驱动,不读无障碍树。

4. **四条"不要做":**
   - 不在组件内加 JSON-LD/schema.org —— Google 官方说对 AI Overviews 无益,且组件不带页面级实体。
   - 不把 `data-*` 当主杠杆 —— 它不进无障碍树,只帮到读原始 DOM 的代理,是弱信号。
   - 不把 L1 当作能独立交付 (a) —— (a) 被消费方站点可抓取性(SSG/SSR)gate 住,那是 L3,库控制不了。
   - 不把 (c)(包内 `llms.txt` / 机器可读组件目录 JSON)当本 skill 杠杆 —— 那是"AI 编码工具用库开发",非 (a)/(b);若用户另需,另开。

5. **ARIA 的双重价值。** 做好 (b) 的 ARIA/语义 HTML,顺带服务屏幕阅读器用户(无障碍),且是组件库本就该有的底子——别把 GEO 和 a11y 对立。

6. **模式由用户定,不擅自动代码。** 先确认本次是**咨询**(出分析/方案)还是要**落地实现**。默认分析先行:产出问题分析、发现、建议、分阶段方案;除非用户明确说"实现/改代码",不要动组件源码。一旦进入实现,每步标注向后兼容风险(见 `levers.md`)。

7. **决策边做边记。** 分析中每产生一个不可逆决策(范围、目标优先级、向后兼容容忍度)或新术语,在**该库自己的**文档里落档:术语表(如 `CONTEXT.md`)+ 决策记录(如 `docs/adr/`)。这是方法的一部分——**不是指向已有文件当真相**,而是边分析边给该库建真相源。某库已有的 ADR/术语表,只是该库的既成决策,不构成 skill 的真相。

## 工作流(定范围 → 查现状 → 诊断 → 方案 → 落档 → 回写)

```
1. 定范围·目标·模式  和用户确认:落在 L1/L2/L3 哪层、a/b/c 优先级、咨询还是落地实现。
                      若实质是 L2/L3 而用户以为在做库,澄清边界
2. 查现状            只读审计相关组件:渲染的根元素/语义元素/ARIA 角色·状态/labeling props/
                      焦点管理,产出差距表(见下方「审计清单」)
3. 诊断              对照 levers.md 杠杆清单 + 该控件类型的 APG 模式,找差距;
                      每条标注:服务 (a) 还是 (b)、证据强度、impact/effort
4. 方案              按 impact/effort 排序给可执行建议;标注哪些是"地基"(b/无障碍)
                      哪些是"顺带 (a)";标注向后兼容风险(DOM/CSS 钩子变更)
5. 落档              把结论写进该库自己的文档(分阶段方案 + 差距表);
                      不可逆决策落 ADR,新术语落术语表
6. 落地后回写        方案进入实施的那一刻起(合并/关闭/部分落地),把结果回写进该库的方案文档:
                      基线双列(审计时/当前)、逐项状态与终局(MR 号/合并时间)、在途批次查
                      远端 MR 列表而非只看本地分支;终局变化时再回写一次
```

### 审计清单(逐组件只读产出)

| 列             | 说明                                                                               |
| -------------- | ---------------------------------------------------------------------------------- |
| 组件           | 组件名                                                                             |
| 类型           | form-control / composite-widget / layout / static                                  |
| 语义元素       | 根/宿主是否 `<button>`/`<input>`/`<nav>`/`<dialog>` 等(✓/✗/部分)                   |
| ARIA 角色      | role=dialog/combobox/listbox/menu/grid/tab/tree…                                   |
| 状态镜像       | aria-expanded/selected/disabled/checked/activedescendant/haspopup 是否同步内部状态 |
| labeling props | aria-label/labelledby/describedby 是否作为组件 prop 暴露                           |
| 焦点管理       | 弹层 trap / roving tabindex / 方向键 / 关闭还原                                    |
| APG 差距       | 对照该控件 APG 模式,缺什么                                                         |

> 审计是只读的:读模板文件(`.vue`/`.tsx`/`.svelte`)与 props/类型定义,不改任何文件。复合控件对照 WAI-ARIA APG 的既成契约(combobox/listbox/menu/menubar/dialog/grid/tabs/tree/accordion 等)。先记原生 seam(已用原生 `<button>`/`<input>`/`<table>`/`<form>` 的组件)——改造在其上加 ARIA,而非重写。
